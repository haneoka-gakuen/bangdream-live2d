# 卡池(Gacha)闪退专项 — 内存优化建议

> 现象: 进入卡池(GachaTop)与抽卡演出/结果界面 频繁闪退
> 范围: `star/Assets/star/Scripts/Gacha/`、`star/Assets/star/Scripts/Screen/ScreenLayers/ScreenLayerGacha*.cs`、`NewSituationIntroduction/`、卡池相关 Dialog
> 配套阅读: 仓库根 `MEMORY_OPTIMIZATION.md`(全局优化)与 `OPTIMIZATION_SKILL.md`(方法论)

---

## 0. 闪退峰值复盘

抽卡链路存在 **三个明显的内存峰值**,从入口到一连结束依次叠加:

```
GachaTop          一次性实例化所有有效卡池的 GachaScreen + 视频/特效预加载
   │
   ▼
GachaConfirmDialog   每次 Resources.Load PaidStoneReminders prefab,无 Unload
   │
   ▼
GachaSpin           三幕 Animator 全开 + 10 张抽到卡 SpinSceneData + 12 个 UITextureLoader + 视频 prefab
   │
   ▼
NewSituationIntroduction  每抽到的角色加载 3 张完整大图(CharacterSituation/BandBg/IntroText) + costume Live2D + bandLogo + voice
   │
   ▼
GachaResult        UIGrid 一次性 Instantiate 10 个 ThumbnailL,常驻 cacheMap
```

**链路上的释放点几乎全集中在 `GachaExecutor.cs:312-315` 的一次 `UnloadUnusedAssets + GC.Collect`**(仅 Spin → Result 之间触发);而 GachaTop OnExit、GachaSpin OnExit、GachaResult OnDispose、二次抽卡入口都没有兜底。链路越长,叠加越严重,低端机在 NewSituationIntroduction 与 GachaSpin 之间最容易爆。

## 2. 最小改动收益最大的 P0 改造(优先级)

下面 6 项做完,预期能消除"进卡池/抽卡过程中突然挂"的绝大多数 case。每一项都聚焦在已确认的释放盲区,改动面小、风险可控。

### P0-1 在三个 ScreenLayer 出口加内存兜底

**位置**:
- `ScreenLayerGachaTop.cs:434-443` `OnExit` 末尾
- `ScreenLayerGachaSpin.cs:203-219` `OnExit` 末尾
- `ScreenLayerGachaResult.cs:155-169` `OnDispose` 末尾

**做法**: 退出动作完成后,等帧调用:

```
yield return null; // 等待 Destroy 完成
Resources.UnloadUnusedAssets();
yield return null;
System.GC.Collect();
System.GC.WaitForPendingFinalizers();
```

把"只在 GachaExecutor.showGachaResult 调一次"扩展到三个出口都调。**这是单点改动收益最大的位置**——挡住三段链路的累积。

### P0-2 修复 GachaSpinScene3 的 Star5 释放遗漏

**位置**: `GachaSpinScene3.cs:1060-1083` `OnFinishAnimation` 与 `:1172-1177` `DestroyTextureLoaders`

**做法**:
1. 在 `OnFinishAnimation` 内,星 5 路径补 `Star5BaseLoader[i].Unload(); Star5EffLoader[i].Unload(); Star5BlurLoader[i].Unload();` 共 9 处。
2. `DestroyTextureLoaders` 内同样追加 Star5 那 9 个 loader 的 OnDestroy。
3. 因为 9 个 loader 共享同一 mainTexture 的 bundle,需要在最后一个 loader Unload 后再调一次 `Atria.UnloadCache(bundleName, fileName)`(可由 `UITextureLoader.Unload` 内部走);若 `Atria.UnloadCache` 引用计数已正确处理共享,9 次 `Unload` 自然会让计数归零。

### P0-3 NewSituationIntroductionExecutor.UnloadResources 补全

**位置**: `NewSituationIntroductionExecutor.cs:171-178`,`:208-224`

**做法**: 现在只 Dispose CharacterSituation,把以下也加入 Dispose:
- bandBackground bundle
- gachaLogo bundle
- introductionText bundle
- costume Live2D bundle(关键大头)
- bandLogo bundle
- voice bundles(若已有 RemoveGachaSpinVoiceBundles 模式则同样处理)

**检查点**: 若有"返回时再次进入需要这些资源"的场景,改成 `OnDispose` 时释放(和现在一致),而不是放在 OnExit。

### P0-4 修补 GachaResult 释放与改用 ScrollView 复用

短期最小化改动:
- `OnDispose` 内追加 `cards.Clear()` 前对所有 cards(无论 Status)调 `Unload()` —— 让 Loading 中的也走释放;然后 `Resources.UnloadUnusedAssets()`(P0-1 已含)
- `clearSituationThumbnails` 内每个 `ct` 在 `Destroy(ct.gameObject)` 前调 `ct.UnloadAndDestroy()`(若有该 API,否则手动 `ct.Unload()`)

中期改造(P1):把 UIGrid 改 RecycleScroll(项目里有 `RecycleScroll`),只渲染当前 ±2 张,瞬时贴图占用从 10 张降到 ~3 张。

### P0-5 GachaTop 视频/卡池预加载延迟化

**位置**: `ScreenLayerGachaTop.cs:370-378`,`:775-815`;`GachaViewControllerBase.cs:287-292`

**做法**:
1. `createGachaViewControllers` 仍然为每条卡池创建 ViewController(轻量),但 `InitializeScreen / InstantiateMovieControllers` 改为"显示当前 tab 时再创建"。
2. CriManaSingle/视频 `Prepare` 仅对当前可见卡池调用,切 tab 时 Dispose 上一个、Prepare 下一个。
3. `GachaCell.attentionTextureLoader.Load` 改为可见时再加载(Cell 进入视口的回调中触发)。

收益: 卡池数 = 8-15 时,GachaTop 进入瞬间峰值能降一倍以上。

### P0-6 BandSelect 5 张 pickup/bg 释放与 unloadAB 修正

**位置**: `BandSelectGachaViewController.cs:91-95`,`:48-57`,`:215-243`;`GachaScreen.cs:262-277`

**做法**:
1. 切换 band 调用 `SetBandSelectGachaAppealImage` 前,对**旧的** `appealImages[i].mainTexture` 与 `bgTexture.mainTexture` 调 `Resources.UnloadAsset`(若是 Atria bundle 资源则 `Atria.UnloadCache`)。
2. `BandLogoLoader.SetLoadOption(true,false,false,false)` 中的 **unloadAB=false 改为 true**(确认是否真有"留缓存以便回切" 的诉求,若有,改为 LRU 上限 2)。
3. `GachaScreen.Destory` 把 `appealImages` / `bgTexture` / `gachaSealAppealTexture` / `screenParticles` 也加入 `useResources` 对应的释放表。

## 5. 测量指标(改造前后必测)

针对卡池闪退专项,推荐打点:

| 节点 | 指标 |
|------|------|
| 进入 GachaTop 前 | 总占用基线 |
| GachaTop OnEnter 完成 | 峰值 vs 基线差 |
| GachaConfirm Dialog 打开 | 增量 |
| GachaSpin OnEnter | 峰值(关键观测点 1) |
| 第 N 张 cutin(N=5/10) | 增量(看星 5 是否累积) |
| NewSituationIntroduction 各角色 | 峰值(关键观测点 2) |
| GachaResult OnEnter | 峰值(关键观测点 3) |
| GachaResult OnDispose 后 | 应回到 GachaTop OnEnter 水位 ±50 MB |
| 重复抽 5 次后回到 GachaTop | 应回到首次基线 ±100 MB(否则有累积) |

打点用 `Profiler.GetTotalReservedMemoryLong / GetTotalAllocatedMemoryLong` + Android `Debug.GetNativeHeapSize` + iOS `os_proc_available_memory`。

**关键回归用例**:
- 一连抽 → 看完 → 返回 GachaTop → 再抽一连 ×10 次,检查峰值不漂移
- 切 BandSelect 卡池的不同 band ×5 次,检查贴图增量
- 进 GachaTop → 切所有 Tab 详情 Dialog ×3 轮,检查内存

## 6. 改造路线图(Sprint 拆分)

### Sprint 1(本周,P0-1 + P0-2 + P0-3 + P0-6 + P1-2)

锁定低改动面、零产品决策、纯代码补漏:

1. 三个 ScreenLayer 出口加 `UnloadUnusedAssets + GC.Collect`(P0-1)
2. GachaSpinScene3 的 Star5 9 个 loader Unload(P0-2)

4. BandSelect 切 band 的旧贴图释放 + `unloadAB=true`(P0-6)
5. CaptureScreen 截屏 Texture2D Destroy(P1-2)

**验收**:Sprint 1 后,在 3GB 设备上完成"GachaTop → 一连抽 → Result → 再抽 → Result"完整循环 ×3 不闪退,峰值漂移 < 100 MB。

### Sprint 2(2 周,P0-4 + P0-5 + P1-1 + P1-4 + P1-7)

1. GachaResult Loading 状态也释放 + UIGrid → RecycleScroll(P0-4 + P2-1 短版)

3. GachaSpinScene3 prefab 资源走 Atria + 释放(P1-1)
4. PaidStoneReminder 改 Atria(P1-4)

**验收**:GachaTop OnEnter 峰值降 30%+;Result 峰值降 50%+(10 → ~3 张同时常驻)。

### Sprint 3(后续,P1-3/P1-5/P1-6/P1-8/P1-9/P1-10 + P2)

按余量推进。

## 8. 与 `MEMORY_OPTIMIZATION.md` 的关系

本文是全局优化中"卡池"这一垂直切片的下钻。若已实施全局 P0:

- 全局 `StarSceneManager` 转场兜底 → 不会触发(本卡池流程在主场景内 ScreenLayer 切换,不走场景兜底)。**所以本文 P0-1 的三处 ScreenLayer 出口兜底必须独立实施。**
- 全局 `Application.lowMemory` 监听 → 对卡池流程是兜底,但属"最后一道",不可替代本文的精细修补。
- 全局 `masterTextureLimit=1` 低端机降级 → 对卡池所有大图(卡面/banner/立绘/cutin)直接生效一倍降幅,**与本文 P0 叠加**,推荐先开降级再做精细修补。
